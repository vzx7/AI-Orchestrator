# AI Orchestrator V5 — Простое руководство

> Этот документ объясняет, как работает система AI Orchestrator, начиная с простых концепций и постепенно переходя к более сложным. Никаких предварительных знаний о распределённых системах не требуется.

> **Текущий статус:** Система находится в статусе **рабочего прототипа**. Основные компоненты (планирование, выполнение, агенты, очередь, DLQ) работают. Некоторые V5-функции (Circuit Breaker, Visibility Reaper) реализованы в коде, но ещё не подключены к основному потоку выполнения.

## 1. Зачем нужна эта система?

Представьте себе такую ситуацию: вы хотите, чтобы AI-агенты автоматически выполнили задачу "Исправить падающий тест и задеплоить сервис". Эта задача на самом деле состоит из нескольких шагов:

1. Найти и исправить код, из-за которого падает тест
2. Запустить тесты, убедиться что всё работает
3. Собрать проект
4. Задеплоить на сервер

Эти шаги частично можно выполнять параллельно, частично — только последовательно. Например, нельзя деплоить, пока не исправлен баг. А вот запустить тесты и поправить документацию можно одновременно.

**AI Orchestrator** — это система, которая:
- Берёт вашу задачу (например, "исправить баг и задеплоить")
- Разбивает её на понятные шаги (план)
- Решает, какие шаги можно выполнять параллельно
- Распределяет шаги по исполнителям (агентам)
- Следит за результатами и повторяет неудачные шаги
- Не теряет работу, если что-то идёт не так

## 2. Основные понятия

### Что такое Задача (Task)?

Это единица работы. Например:
- "Исправить функцию `calculateTotal` в файле `cart.go`"
- "Запустить unit-тесты"
- "Задеплоить сервис в production"

У каждой задачи есть:
- **ID** — уникальный номер
- **Название** — что делать
- **Статус** — pending (ожидает), running (выполняется), done (готово), failed (провалена)
- **Агент** — кто должен выполнить (Developer, QA, Ops)

### Что такое Агент?

Это специализированный AI-бот, который умеет делать определённые вещи:

| Агент | Что умеет |
|-------|-----------|
| **Developer** | Писать код, исправлять баги, делать коммиты |
| **QA** | Запускать тесты, проверять качество |
| **Ops** | Деплоить, управлять инфраструктурой |

Агент получает задачу и выполняет её, используя доступные инструменты (читать файл, запустить команду, сделать deploy).

### Что такое План (Plan)?

Это граф задач с зависимостями. Говоря проще — это список задач, где указано, какая задача от какой зависит.

Пример:
```
[Исправить код] ──→ [Запустить тесты] ──→ [Задеплоить]
       │
       └──────────────────────────→ [Обновить документацию]
```

Стрелки показывают: "эту задачу можно начать только после завершения предыдущей".

### Что такое Очередь (Queue)?

Очередь — это место, где задачи ждут своего исполнителя. Представьте её как список дел:

1. Задача приходит → попадает в очередь (pending)
2. Исполнитель готов → берёт задачу из очереди (dequeue), начинает делать (running)
3. Исполнитель закончил → помечает задачу как выполненную (ack)
4. Что-то пошло не так → говорит "не получилось, попробуйте ещё раз" (nack с retry)

Это гарантирует: **ни одна задача не потеряется**, даже если исполнитель вдруг упадёт.

### Что такое Worker (Исполнитель)?

Worker — это процесс (компьютерная программа), которая:
- Подключается к оркестратору
- Говорит "я готов выполнять задачи"
- Получает задачи по сети (gRPC)
- Выполняет их через агентов
- Возвращает результат

Worker может быть запущен на любом компьютере — локально, на сервере, в облаке.

## 3. Как задача проходит путь от начала до конца

Разберём пошагово, что происходит, когда вы отправляете задачу "Исправить баг и задеплоить":

### Шаг 1: Планирование (Planner)

Вы отправляете запрос: `"Fix the failing test and deploy the service"`

**Planner** (планировщик) анализирует запрос и создаёт план:
- Какие задачи нужно выполнить?
- Какая задача от какой зависит?
- Какие задачи можно выполнять параллельно?

Результат — структура данных (DAG — Directed Acyclic Graph), граф задач с зависимостями.

### Шаг 2: Управление (Controller)

**Controller** — это "мозг" системы. Он реализует цикл:

```
План → Выполнение → Оценка → Перепланирование (если нужно)
```

 Controller следит за ходом выполнения:
- Все ли задачи выполнены?
- Какие задачи провалились?
- Нужно ли повторить неудачную задачу?
- Пора ли переделать весь план?

### Шаг 3: Выполнение (Executor)

**Executor** берёт план и выполняет задачи:
- Находит задачи, которые готовы к выполнению (их зависимости уже завершены)
- Запускает их параллельно, если это возможно
- Ждёт результаты

### Шаг 4: Оценка (Evaluator)

После каждой задачи **Evaluator** смотрит на результат:
- Задача выполнена успешно? → двигаемся дальше
- Задача провалилась? → пробуем ещё раз или меняем план

### Шаг 5: Работа Агентов

Агент получает задачу и выполняет её:
1. Выбирает нужный инструмент (читать файл, запустить команду и т.д.)
2. Tool Gateway проверяет, разрешено ли агенту использовать этот инструмент (ACL)
3. Инструмент выполняет действие (или mock-заглушка в текущей версии)
4. Агент возвращает результат

### Шаг 6: Сохранение контекста

**Context Manager** запоминает всё, что произошло:
- Какие задачи выполнены
- Какие результаты получены
- Что было важно, что менее

Это нужно, чтобы последующие задачи "понимали", что уже было сделано.

### Компоненты оркестратора

| Компонент | Зачем нужен |
|-----------|-------------|
| **Planner** | Превращает запрос в план задач с зависимостями |
| **Controller** | Управляет циклом Plan→Execute→Evaluate→Replan |
| **Executor** | Выполняет задачи, параллельно если возможно |
| **Evaluator** | Оценивает результаты, решает что делать дальше |
| **Queue** | Надёжная очередь с подтверждениями (Ack/Nack) |
| **Registry** | Регистр воркеров, выбор кто выполнит задачу |
| **RPC Client** | Общение с удалёнными воркерами |
| **Context Manager** | Запоминает результаты для последующих шагов |
| **Event Bus** | Позволяет подписаться на события (для логирования) |

### Компоненты воркера

| Компонент | Зачем нужен |
|-----------|-------------|
| **Agent (Dev/QA/Ops)** | Выполняет задачи своей специализации |
| **Tool Gateway** | Проверяет права агента на инструменты |
| **MCP Registry** | Хранит доступные инструменты |
| **Circuit Breaker** | ⚠️ Код реализован, но не подключён (V5) |

## 5. Как система справляется с ошибками

Это одна из самых важных частей системы. AI Orchestrator разработан так, чтобы **не терять работу** даже при сбоях.

### 5.1 Очередь с подтверждениями (Ack/Nack)

Обычная проблема: "А что если воркер взял задачу, начал делать, и вдруг упал?"

Решение: Очередь отслеживает, какая задача у какого воркера.

```
1. Воркер берёт задачу из очереди → задача помечается как "в работе"
2. Воркер закончил → воркер говорит "готово" (Ack) → задача удаляется
3. Воркер упал на середине → задача "висит" в статусе "в работе"
```

Через 60 секунд специальный процесс (Visibility Reaper) должен проверять:
- "Эта задача ещё в работе? Она не должна висеть так долго!"
- Задача возвращается обратно в очередь для другого воркера.

> ⚠️ **Примечание:** Visibility Reaper реализован в коде, но не запускается в текущей версии main.go.

### 5.2 Автоповтор неудачных задач (Retry with Jitter)

Если задача провалилась, система попробует ещё раз:
- 1-я попытка → подождать 1 сек
- 2-я попытка → подождать 2 сек
- 3-я попытка → подождать 4 сек
- ...и так далее

**Jitter** (дрожание) добавляет случайность ±30% к времени ожидания. Это нужно, чтобы все воркеры не начали повторять одновременно (thundering herd problem).

### 5.3 Circuit Breaker (Автоматический выключатель)

Представьте: один воркер начал сбоить — отвечает медленно или с ошибками. Если отправлять ему задачи, система будет ждать таймаутов и тормозить.

**Circuit Breaker** работает как автоматический выключатель в доме:
- Воркер сбоит 5 раз подряд → автоматически отключается
- Задачи больше не отправляются этому воркеру
- Через 30 секунд — проверка: "Может, уже работает?"
- Если работает — снова подключаем

### 5.4 Dead Letter Queue (Очередь мёртвых задач)

После максимума попыток (по умолчанию 10) задача всё ещё может не выполниться. Вместо того чтобы бесконечно повторять, она попадает в **DLQ** — специальное хранилище для провалившихся задач.

Из DLQ задачу можно:
- Посмотреть причину провала
- Исправить проблему вручную
- Попробовать ещё раз

### 5.5 Idempotent Execution (Идемпотентность)

Проблема: "А что если задача уже выполнена, но мы её повторяем из-за сбоя?"

Решение: у каждой задачи есть **idempotency key** (ключ идемпотентности). Перед выполнением система проверяет: "Эта задача уже выполнялась?" Если да — возвращается сохранённый результат, задача не выполняется повторно.

### 5.6 Защита от бесконечных циклов

Controller ограничивает:
- Максимум 1000 итераций на план
- Максимум 3 перепланирования
- Если 3 перепланирования подряд не дали прогресса — аборт

## 6. Как работает распределённый режим

Все примеры выше — для одного процесса (local mode). Но систему можно запустить в распределённом режиме:

### Запуск

```bash
# Терминал 1: Запускаем оркестратор
go run ./cmd/orchestrator/ --distributed

# Терминал 2: Запускаем воркер 1
go run ./cmd/worker --id=worker-1 --addr=localhost:50051

# Терминал 3: Запускаем воркер 2
go run ./cmd/worker --id=worker-2 --addr=localhost:50052
```

### Как это работает

```
┌─────────────────┐      демо-RPC     ┌─────────────────┐
│   Orchestrator  │◄───────────────────│    Worker 1     │
│                 │                    │   (Agent Dev)   │
│   [Планировщик] │ ───────────────────▶│   [Agent QA]    │
│                 │ ────────────────────▶│   [Agent Ops]   │
│   [Очередь]     │                    └─────────────────┘
│                 │      демо-RPC     ┌─────────────────┐
│                 │◄───────────────────│    Worker 2     │
│  [Registry:     │                    │   [Agent Dev]   │
│   worker-1 ✓    │ ────────────────────▶│   [Agent QA]    │
│   worker-2 ✓]   │                    └─────────────────┘
└─────────────────┘
```

> ⚠️ **Важно:** Текущая реализация использует **демо-RPC** (прямые вызовы Go функций в одном процессе). Реальный gRPC и сетевое взаимодействие между отдельными процессами ещё не реализованы.

1. Воркеры регистрируются в Registry: "Я here, готов принимать задачи"
2. Воркеры периодически отправляют heartbeat: "Я alive"
3. Если воркер не отправлял heartbeat 30 секунд — он считается мёртвым
4. При отправке задачи Registry выбирает воркера с наименьшей нагрузкой

### Выбор воркера (Load Balancing)

Registry знает:
- Кто currently healthy
- Сколько задач currently active у каждого воркера
- Среднее время отклика каждого воркера

Выбирается воркер:
1. Только healthy (живые)
2. Не на максимальной capacity
3. Среди оставшихся — с наименьшим количеством active задач
4. Если несколько — с наименьшим latency

## 7. Новые возможности версии V5

Версия V5 добавила несколько важных улучшений для production-использования:

| Возможность | Статус | Как работает |
|-------------|--------|--------------|
| **Circuit Breaker** | ⚠️ В коде, не подключён | 3 состояния: Closed → Open → Half-Open. Готов к подключению. |
| **Visibility Timeout Reaper** | ⚠️ В коде, не запускается | Фоновая проверка каждые 10 сек. Нужно вызвать `reaper.Start()` |
| **Retry with Jitter** | ✅ Работает | ±30% случайности к времени повтора. |
| **Latency-Aware LB** | ✅ Работает | Учитывает нагрузку и latency при выборе воркера. |
| **Context Relevance Scoring** | ✅ Работает | Оценка важности результатов: 60% от свежести + 40% от важности. |
| **State Transition Validation** | ✅ Работает | Проверка: можно ли перейти из одного состояния в другое. |

## Резюме

AI Orchestrator — это система, которая берёт сложную задачу, разбивает её на понятные шаги, выполняет их надёжно (с повторами при сбоях) и распределяет по специализированным агентам.

**Ключевые принципы:**
1. **Надёжность** — ни одна задача не потеряется благодаря очереди с подтверждениями
2. **Устойчивость к сбоям** — автоматические повторы, DLQ, восстановление зависших задач
3. **Масштабируемость** — можно добавлять воркеры без изменения кода
4. **Распределённость** — воркеры работают удалённо, общаются по gRPC *(в разработке)*
5. **Интеллект** — система сама решает, что делать при ошибках (повторить или изменить план)
